# Инструмент "Расход" для Yonda Cards — дизайн

## Контекст

Из восьми веток старой Google-формы "Учет Yonda Cards" ветка **Продажа**
уже перенесена в новый веб-инструмент (`sales.html`, GitHub Pages +
Apps Script backend), а часть учёта товаров — в **Инвентаризацию**
(`inventory.html`). Остаются: Переводы, Расход, и часть "Учёт товаров"
(Производство, Перемещение между складами). Это отдельные, независимые
друг от друга инструменты — договорились разбить их на отдельные
под-проекты, каждый со своим циклом spec → план → реализация, как было
с корзиной продаж. Этот документ — первый из них: **Расход**.

Доход (доход без привязки к товару) в объём этой работы не входит —
он ещё не мигрирован, но это отдельный вопрос на будущее.

Система данных не меняется: единая Google Таблица, где напрямую
пишутся только два листа — `Ответы на форму (1)` (сырые события,
Layer 1) и `Справочники` (справочные таблицы, ручной ввод); все
остальные листы (`Операции`, `Счета`, `P&L` и т.д.) — формулы поверх
этих двух. Новый инструмент, как и корзина продаж, пишет только через
`Ответы на форму (1)`.

## Текущая система: ветка "Расход"

Сверено напрямую с рабочей таблицей ("test Yonda фин учет",
лист `Справочники`, столбец G и лист `Ответы на форму (1)`):

**`Справочники!G2:G12`** — 11 категорий расхода:
Услуги полиграфии, Расходные материалы, Маркетинг, Оборудование,
Налоги, Транзакционные расходы, Личные расходы, ФОТ, Аренда,
Транспортные расходы, Прочее.

**`Справочники!D:E`** ("Тип оплаты → Счёт", уже используется
`getPaymentTypes()` для продаж) — та же таблица переиспользуется для
Расхода без изменений: Наличка→Наличка, Paynet→Paynet, Перевод на
карту→Личная карта, Click→Расчётный счёт, Payme→Расчётный счёт,
Личная карта→Личная карта, Расчётный счёт→Расчётный счёт.

**`Ответы на форму (1)`, ветка Расход** (1-based; подтверждено по
живому листу и совпадает с индексами в `Уведомления через ТГ-бот.js`):
`B` = Тип записи ("Расход"), `G` = Категория, `H` = Сумма,
`I` = Тип оплаты, `J` = Примечание.

**Важный нюанс, подтверждённый в коде продаж** (`appendIncomeRow_`,
`AppScripts/InventoryService.gs`): в колонку `Тип оплаты` пишется не
сырой ярлык, который видит кассир, а **уже разрешённый счёт** (значение
из `Справочники!E`) — потому что формула `Операции`, судя по всему,
копирует эту колонку как есть, без собственного поиска по
`Справочники!D:E`. Расход обязан писать так же: разрешать тип оплаты в
счёт на сервере **до** записи, и отказывать в записи, если
соответствия нет — иначе в финансовый журнал попадёт непроверенное
значение.

Уже существующая функция `handleExpenseNotification` в
`Уведомления через ТГ-бот.js` шлёт Telegram-сообщение о новом расходе
("💸 Расход / Категория / Сумма / Счёт") — но триггер `onFormSubmit`,
на котором она висит, срабатывает только при отправке настоящей
Google-формы, не при программной записи строки через Apps Script.
Поэтому, как и в случае с продажами (`submitSale` шлёт своё
Telegram-сообщение сам, не полагаясь на легаси-триггер), новый
инструмент обязан отправлять уведомление явно из своего кода.

## Дизайн

### Архитектура

Отдельный, изолированный инструмент — по той же схеме, что и корзина
продаж: одна ветка старой формы → один новый файл фронтенда + один
файл бэкенда. Рассматривались варианты держать логику расхода внутри
`InventoryService.gs` или сделать один общий инструмент "Доход/Расход"
— оба отклонены: первый смешивает несвязанные обязанности в уже
растущем файле, второй выходит за рамки согласованного объёма (только
Расход сейчас) и не имеет прецедента в проекте (каждая ветка формы уже
стала отдельным инструментом).

Новые файлы:
- `WebFrontend/expense.html` — фронтенд.
- `AppScripts/ExpenseService.gs` — точки входа API (`getExpenseCategories`, `submitExpense`) и запись в лист.
- `AppScripts/Lib/ExpenseLogic.js` — чистая, юнит-тестируемая логика (валидация, сборка строки, Telegram-сообщение), без зависимости от `SpreadsheetApp` — по образцу `Lib/SalesLogic.js`.
- `AppScripts/Lib/ExpenseLogic.test.js` — юнит-тесты, по образцу `SalesLogic.test.js`.

Переиспользуется без изменений: `getPaymentTypes()` и `resolveAccount()`
(уже есть в `InventoryService.gs`/`SalesLogic.js` — это общая логика,
не специфичная для продаж), вся схема авторизации (Google ID token +
`ALLOWED_EMAILS`), диспетчер действий в `Api.gs`, стиль ошибок
(`jsonResponse_({error: ...})` с понятным русским текстом).

### Бэкенд

**`getExpenseCategories()`** — читает `Справочники!G2:G` динамически
(до первой пустой ячейки), по образцу `getLocations()`/`getPaymentTypes()`.
Возвращает массив строк.

**`submitExpense(category, amount, paymentType, note)`**:
1. Валидация: `category` — непустая строка (из списка, но сервер не
   обязан жёстко валидировать по списку — как и с товарами, список
   на клиенте уже ограничивает выбор); `amount` — число > 0.
2. Разрешение счёта **до записи**: `resolveAccount(getPaymentTypes(), paymentType)`.
   Если `null` — бросить ошибку с понятным текстом ("Тип оплаты «...»
   не сопоставлен со счётом в Справочники!D:E — расход не записан.") и
   не писать ничего. Точная копия защитной логики `submitSale`.
3. Запись одной строки в `Ответы на форму (1)`: `A` = текущее время,
   `B` = "Расход", `G` = category, `H` = amount, `I` = resolvedAccount,
   `J` = note (может быть пустым — необязательное поле, как и в
   исходной форме).
4. Telegram-уведомление тем же форматом, что и `handleExpenseNotification`
   ("💸 Расход / Категория / Сумма / Счёт"), отправленное явно из кода.
5. Возврат `{ written: true }` (или аналогичная простая структура) на успех.

**Новые действия в `Api.gs`**: `getExpenseCategories` (GET),
`submitExpense` (POST) — добавляются в существующие
`handleApiGet_`/`handleApiPost_` тем же способом, что и действия
продаж/инвентаризации.

### Фронтенд (`expense.html`)

Гораздо проще корзины продаж — это одна запись, не список позиций:

- При загрузке: параллельно `getExpenseCategories()` и
  `getPaymentTypes()` (обе — уже привычный паттерн ретрая при ошибке
  загрузки, как в `sales.html`).
- Форма: категория — чипы (11 штук, сетка с переносом строк, тот же
  визуальный компонент, что и чипы типа оплаты в `sales.html`); сумма
  — числовое поле; тип оплаты — чипы (переиспользуемые как есть);
  примечание — необязательное текстовое поле.
- **Тип оплаты во фронтенде показывает только столбец D** (`getPaymentTypes()[].type`).
  Столбец E (разрешённый счёт) **нигде не отображается в UI** — ни в
  чипах, ни на экране подтверждения; он существует только на сервере,
  чтобы `submitExpense` знал, что записать в колонку `I` листа
  `Ответы на форму (1)`. Экран подтверждения после записи показывает
  категорию, сумму и выбранный тип оплаты (D) — без счёта.
- Кнопка "Записать расход" активна только когда категория, сумма (> 0)
  и тип оплаты выбраны.
- Экран подтверждения (галочка, категория, сумма, тип оплаты) — по
  образцу экрана подтверждения продажи. Кнопка "Новый расход" сбрасывает
  форму, но оставляет последний выбранный тип оплаты (та же UX-конвенция,
  что и в продажах).
- Обработка ошибок: тот же `onError` (истёкший токен → алерт + принудительный
  выход), общая ошибка сервера — алерт с текстом из `err.message`.
- Одна новая ссылка `card-btn` в `WebFrontend/index.html`.

### Тестирование

`Lib/ExpenseLogic.test.js` — юнит-тесты (без GAS-окружения):
сборка строки для записи, случаи отказа `resolveAccount` (тип оплаты
не найден в списке / найден, но счёт пустой), сборка текста
Telegram-сообщения. По структуре — копия `SalesLogic.test.js`,
адаптированная под одну запись вместо чека из нескольких позиций.

## Вне объёма (сознательно не делаем)

- Доход, Переводы, Производство, Перемещение между складами — отдельные под-проекты.
- Управление списком категорий/типов оплаты через UI — по-прежнему правится вручную в `Справочники`.
- Валидация категории на сервере строго по списку — клиент уже ограничивает выбор чипами; сервер доверяет непустой строке (как и с товарами в продажах).
- Оффлайн-режим.

## Открытые вопросы для этапа реализации

- Таблица, по которой сверялась структура ("test Yonda фин учет") —
  судя по названию, вероятно тестовая копия, а не продовая таблица (в
  документации предыдущих этапов тоже упоминается "песочница"). Структура
  столбцов не должна отличаться, но перед деплоем нужно уточнить у
  владельца, какая таблица — реальная продовая, и что Apps Script проект
  разворачивается именно на неё.
- Легаси-триггеры (`handleTransfer`, `handleProduction`,
  `onEditProduction`, `handleExpenseNotification` и другие функции в
  `Уведомления через ТГ-бот.js`) — их фактическое состояние (установлены
  ли на проде) не проверялось в рамках этой работы; новый инструмент
  от них не зависит (шлёт Telegram сам), так что это не блокирует
  реализацию, но стоит иметь в виду при финальной проверке на проде.

## Критерии готовности

- Расход с каждым типом оплаты (7 штук) корректно резолвится в
  правильный счёт; строка в `Ответы на форму (1)` содержит верные
  значения по всем 4 колонкам (Категория/Сумма/Тип оплаты как счёт/Примечание).
- Расход с типом оплаты, для которого нет соответствия (тестовый
  случай с намеренно некорректным значением) — сервер отклоняет
  запрос с понятной ошибкой, строка в лист **не** добавляется.
- Telegram-уведомление приходит с корректной категорией, суммой и
  счётом сразу после успешной записи.
- Посторонний Google-аккаунт (не из `ALLOWED_EMAILS`) не может вызвать
  ни одно из двух новых действий API.
- Форма на телефоне: чипы категорий и типа оплаты не переполняют
  экран, сумма вводится числовой клавиатурой, "Новый расход" сбрасывает
  форму и сохраняет последний тип оплаты.
