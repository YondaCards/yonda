# Инвентаризация и корзина продаж для Yonda Cards — дизайн

## Контекст

Yonda Cards — домашнее производство открыток, альбомов и интерактивных книг
(Ташкент, сум). Продажи идут через Instagram, индивидуальные заказы и пять
офлайн-точек на консигнации (Teplo Store TAS, Teplo Store SKD, Human House,
UzPost, Ethno Gallery). У бизнеса уже есть рабочий инструмент управленческого
учёта — Google Таблица "test Yonda фин учет", связанная с Google-формой
"Учет Yonda Cards" и несколькими Apps Script автоматизациями (Telegram-бот,
уведомления о заказах, автосписание материалов при производстве).

Таблица активно используется (899+ строк в журнале операций), но два процесса
в ней неудобны, из-за чего фактически не используются на практике. Эта работа
— два новых мобильных инструмента поверх существующей таблицы, без замены
самой системы учёта.

## Текущая система (по состоянию на 31.08.2026)

### Листы таблицы

| Лист | Назначение |

| Ответы на форму (1) | Сырые ответы Google-формы "Учет Yonda Cards" (ветки: Продажа/Расход/Доход/Переводы/Учёт товаров) |

### Формула остатка «Склад товаров» (на каждую ячейку Товар×Локация)

```
=СУММЕСЛИМН(Кол-во; Товар; Тип="Производство"; Куда=локация)
+СУММЕСЛИМН(...; Тип="Перемещение"; Куда=локация)
+СУММЕСЛИМН(...; Тип="Возврат"; Куда=локация)
+СУММЕСЛИМН(...; Тип="Заказ у поставщиков"; Куда=локация)
−СУММЕСЛИМН(...; Тип="Перемещение"; Откуда=локация)
−СУММЕСЛИМН(...; Тип="Продажа"; Откуда=локация)
−СУММЕСЛИМН(...; Тип="Возврат"; Откуда=локация)
```

### Google-форма "Учет Yonda Cards" — текущие ветки

- **Продажа**: Товар (один!), Количество, Тип оплаты, Примечание. Без точки/канала, без цены.
- **Расход**, **Доход**, **Переводы**: не затрагиваются этой работой.
- **Учёт товаров → Пополнение**: Тип операции (Производство/Возврат/Заказ у поставщиков), Товар, Количество, Примечание. Форма явно предупреждает: "Запись товара с типом Производство влечёт списание Материалов со склада".
- **Учёт товаров → Перемещение**: не осмотрено детально, не затрагивается этой работой.

### Существующие Apps Script файлы (папка `AppScripts/`)

Имена файлов не соответствуют содержимому (легаси-путаница, менять не обязательно):

- `OrderHandler.gs` — на самом деле: Telegram-уведомления при отправке формы (Продажа/Расход/Доход/Переводы), ежедневный отчёт в 8:00, Telegram-бот вебхук (`/баланс`, `/отчет`).
- `ProductionHandler.gs` — на самом деле: обработка денежных переводов между счетами (`handleTransfer`), пишет зеркальную строку зачисления + комиссию в "Ответы на форму (1)".
- `Переводы.gs` — на самом деле: автосписание материалов при производстве (`handleProduction`, `onEditProduction`, `writeOffMaterials`). Читает BOM из "Справочники" (столбцы M:P), проверяет достаточность остатка материалов, пишет списания в "Реестр материалов".
- `Уведомления.gs` — Telegram-уведомления о новых заказах из "Заказы клиентов" + напоминание за 2 часа до доставки.

**Обнаруженный баг**: `onEditProduction` в `Переводы.gs` слушает изменение столбца **3** (`C` = "Тип записи") в листе "Реестр товаров", но значение "Производство" по факту вводится в столбец **6** (`F` = "Тип"). Похоже на рассинхронизацию после того, как в лист добавили столбцы `ID`/`Тип записи`. Пользователь не уверен, работает ли сейчас автосписание при ручном вводе — считаем багом, чиним и тестируем в рамках этой работы.

## Проблемы, которые решает эта работа

1. **Нет инструмента инвентаризации.** Чтобы выровнять остаток под фактический подсчёт, сейчас нужно вручную вычислять и вписывать корректирующую дельту в реестр. Хочется просто вписать фактическое количество по каждой позиции.
2. **Списание при продаже неудобно**, поэтому на практике вписывается только доход деньгами, а остатки товаров не ведутся — накапливается расхождение с реальностью (в остатках уже есть отрицательные значения, например "О маме" −3 на Основном складе).
3. **Форма для продаж негибкая**: один товар за раз, без корзины из нескольких позиций, без видимости остатка на месте ввода.

Пользоваться новыми инструментами будут только владелец и партнёр (у обоих отдельные Google-аккаунты), **в основном с телефона**.

## Дизайн

### Архитектура

Отдельное **Google Apps Script Web App** (`doGet()`, HTML/CSS/JS), развёрнутое из того же скрипт-проекта, что уже привязан к таблице (переиспользует доступ к `SpreadsheetApp`). Открывается по прямой ссылке в любом мобильном браузере; можно добавить на домашний экран телефона.

- Развёртывание: "Выполнять от имени: меня" / "Доступ: любой с Google-аккаунтом".
- Внутри скрипта — проверка `Session.getActiveUser().getEmail()` по списку из двух адресов (владелец + партнёр). Для всех остальных — экран "Нет доступа".
- Меню внутри самой таблицы не добавляем — единственная точка входа это ссылка на веб-приложение.
- Функционально не работает офлайн (нужен интернет — как и сама Google Таблица).

### Инструмент 1: Инвентаризация

**Экран выбора**: Материалы, или Товары (для товаров — дополнительно выбор локации: Основной склад или одна из 5 точек).

**Экран подсчёта**: список позиций (Материал/Товар, единица измерения) с текущим расчётным остатком и пустым полем "Факт". Мобильная раскладка — один столбец, крупные поля, числовая клавиатура. Позиции без изменений оставляются пустыми.

**Сохранение**: для каждой заполненной строки считается `дельта = факт − текущий остаток`. Строки с дельтой 0 или пустым полем пропускаются (без записи в журнал, чтобы не засорять его).

- **Материалы** → строка в "Реестр материалов": `Тип = "Приход"` (дельта > 0) или `"Списание"` (дельта < 0), `Количество = |дельта|`, `Примечание = "Инвентаризация от {дата}"`. Формула остатка не меняется — уже поддерживает эти два типа.
- **Товары** → строка в "Реестр товаров": новый `Тип = "Инвентаризация"`, `Куда = локация` (дельта > 0) или `Откуда = локация` (дельта < 0), `Количество = |дельта|`. **Требуется расширить формулу остатка** в "Склад товаров" (по всей сетке Товар×Локация) двумя дополнительными слагаемыми СУММЕСЛИМН — по аналогии с "Возврат".

### Инструмент 2: Корзина продаж

**Пересмотрено 03.09.2026** по итогам обсуждения с владельцем — см. изменения ниже относительно первоначального дизайна.

**Каталог (без выбора точки на входе)**: список товаров из "Справочник цен" с остатком **всегда по "Основной склад"**, плюс поле поиска. Точка/канал продажи выбирается позже, только как атрибут для "Операции"/отчётности — она **не влияет** на то, откуда списывается остаток: списание всегда идёт с "Основной склад", независимо от того, где физически проходит продажа (мотив: на выставках/в точках физически продают то, что было заранее взято с основного склада, а вести отдельный остаток по каждой точке на практике не получается — см. уже накопленные расхождения, п. "Проблемы" выше).

**Чек**: нажатие на позицию каталога добавляет её в чек с количеством 1 и ценой из "Справочник цен". В чеке можно: менять количество; менять цену вручную (позиция помечается как "цена изменена вручную", в итог и в запись идёт указанная цена, а не цена из прайса); добавлять свободную позицию (название + сумма вручную, без привязки к каталогу и остаткам) — для услуг и уникальных вещей, которых нет на складе. Чек может одновременно содержать и складские позиции, и свободные. Мягкое предупреждение при уходе остатка в минус (не жёсткий запрет — продажи иногда вносятся задним числом).

**Оформление**: точка/канал (справочник "Точки продаж") и тип оплаты — оба поля предзаполнены последним использованным значением за сессию, чтобы не выбирать их заново на каждую продажу подряд.

**Запись при подтверждении** (одно нажатие, одна транзакция): на чек из N складских позиций + M свободных (услуг) пишется **N + 1 строка**, не N+M — свободные позиции не получают собственной строки движения товара, они существуют только внутри одной денежной строки:
- по одной строке **на каждую складскую** позицию чека в "Реестр товаров" (через тот же путь Layer 1 → Layer 2, что и у "Учёт товаров", т.е. запись через "Ответы на форму (1)"): `Тип записи = "Учет товаров"`, `Вид действия = "Продажа"`, `Товар`, `Количество`, `Откуда = "Основной склад"`, `Куда = ""`. Как и всегда в "Реестр товаров"/"Склад товаров", **цены в этой строке нет вообще** — только название и количество, ценой этот слой никогда не занимался. Свободные позиции (услуги) сюда не попадают — списывать нечего;
- ровно **одна** строка в "Операции" (через ветку "Доход" формы) на весь чек целиком: `Тип = "Доход"`, `Сумма = сумма всего чека` (складские позиции + свободные, по цене, которая реально стояла в момент продажи — включая ручные переопределения), `Счёт = выбранный тип оплаты` (без отдельной карты соответствия — тип оплаты в этом инструменте это и есть название счёта: "Наличка" / "Paynet" / "Карта (личная)" / "Расчётный счёт ИП", те же четыре значения, что уже пишет в "Тип оплаты" ветка "Доход" текущей формы и знает `accountIcons` в `Уведомления через ТГ-бот.js`), `Категория = "Продажа товаров"`, `Примечание` = **построчно** `название x количество = сумма` для каждой позиции чека (включая свободные) — единственное место, где сохраняется, по какой именно цене ушла каждая позиция, раз "Реестр товаров" цену не хранит, а `Сумма` этой строки — это только общий итог;
- Telegram-уведомление с составом чека (по той же построчной разбивке), точкой/каналом, типом оплаты и итогом.

**Откуда берётся сумма.** Сервер не пересчитывает цену из "Справочник цен" в момент продажи (в отличие от старой ветки "Продажа", где `getPriceByProduct` искал цену только в момент отправки Telegram-уведомления, а сама форма цену вообще не хранила). Инструмент продаж уже знает точную цену каждой позиции чека на клиенте — из прайса или введённую вручную — и именно её отправляет на сервер; сервер лишь умножает `цена × количество` и суммирует. Это и есть механизм, которым ручное переопределение цены доходит до записи: она просто есть в теле запроса, и никакого отдельного поля/колонки под неё заводить не нужно.

Этот инструмент **полностью заменяет ветку "Продажа"** в Google-форме. Ветки Расход/Доход/Переводы/Учёт товаров в форме не меняются.

**Тип оплаты и точки продаж для v1**: захардкожены константой в коде инструмента (а не читаются из "Справочники"), так как точные заголовки соответствующих колонок в "Справочники" не были сверены на момент дизайна. Если позже понадобится редактировать эти списки без изменения кода — вынести в лист по образцу `getLocations()`.

#### Особый случай: открытки (много видов, одна цена)

Видов открыток очень много, у всех одна и та же цена, а на выставке нет времени разбирать, какого именно вида ушла каждая открытка. Решение:

- В каталоге и "Справочник цен" открытки представлены **одной агрегированной позицией "Открытка"** (отдельная строка, отдельная своя формула остатка в "Склад товаров", как у любого обычного товара) — конкретные виды (например, "О маме", "Про любовь") в каталог корзины продаж **не выводятся**.
- Продажа "Открытка" ничем не отличается от продажи любого другого товара — отдельного кода в инструменте продаж не требуется. Строка в "Реестр товаров" пишется с `Товар = "Открытка"`, и её остаток списывается формулой ровно как у любого другого товара.
- Остатки **по конкретным видам** открыток не ведутся в реальном времени во время выставки — они не так важны для оформления заказа, но нужны для последующего анализа, какие виды продаются лучше.
- **Сверка по видам — после выставки**, через существующий инструмент "Инвентаризация" (Товары → Основной склад), где виды открыток по-прежнему считаются по отдельности (агрегированная позиция "Открытка" в списке для подсчёта не показывается — её никто вручную не считает). На экране подсчёта товаров добавляется переключатель **"Это сверка продаж"**, который меняет то, как трактуется отрицательная дельта у конкретного вида открытки:
  - **Дельта положительная** (нашли больше, чем числилось — пришла новая партия) → как сегодня, `Вид действия = "Инвентаризация"` по этому виду, **и дополнительно** пишется вторая, зеркальная строка `Товар = "Открытка"` (агрегат) с той же величиной и направлением — чтобы общий остаток "Открытка" тоже вырос.
  - **Дельта отрицательная, переключатель включён** (открытки разошлись на выставке) → `Вид действия = "Продажа"` по этому виду, `Откуда = "Основной склад"`. Агрегат "Открытка" **не трогаем** — он уже был списан в реальном времени в момент продажи в Корзине.
  - **Дельта отрицательная, переключатель выключен** (обычная недостача/порча вне контекста выставки) → как сегодня, `Вид действия = "Инвентаризация"` по этому виду, **и дополнительно** зеркальная строка `Товар = "Открытка"` с той же (отрицательной) величиной — реальная потеря, которую агрегат ещё не учитывал.
- Ни в одном из случаев инструмент не пишет напрямую в ячейку остатка — только новые строки в "Реестр товаров" (через "Ответы на форму (1)"), как и весь остальной код этого проекта; остаток агрегата "Открытка" всегда пересчитывается той же формулой СУММЕСЛИМН, что и у обычного товара, просто по строкам с `Товар = "Открытка"`.
- **Разовая ручная подготовка** (не код): владелец добавляет "Открытка" как новую позицию в "Справочник цен" (с обычной ценой открытки) и как новый товар в "Склад товаров" — вторым способом проще всего через уже существующую функцию "добавить новую позицию" в самой "Инвентаризации" (ввести "Открытка" и текущее суммарное количество открыток всех видов). Отдельно владелец даёт разработчику точный список названий видов открыток, как они записаны в "Справочник цен" — этот список зашивается в код (константа), а не читается из отдельного столбца-признака в таблице.

### Попутное исправление

Поправить `onEditProduction` в `Переводы.gs`: слушать столбец `F` ("Тип"), а не `C` ("Тип записи"), чтобы ручной ввод "Производство" в "Реестр товаров" действительно списывал материалы. Проверить и `handleProduction` (form-submit версию) на соответствие текущей структуре листов.

## Критерии готовности

- Инвентаризация: тестовый прогон по 2–3 позициям материалов и товаров (в т.ч. на локации-точке), остатки после сохранения совпадают с введённым фактом, лишние строки не создаются для пустых полей.
- Корзина: тестовая продажа из 2+ складских позиций плюс одной свободной позиции (услуги), с ручным изменением цены хотя бы одной позиции — после оформления остаток "Основной склад" уменьшился на нужное количество по каждой складской позиции (свободная позиция остаток не трогает), в "Операции" появилась одна строка с суммой всего чека и верным счётом, Telegram-уведомление пришло с полным составом чека.
- Открытки: тестовая продажа позиции "Открытка" уменьшает остаток агрегата "Открытка", но не трогает остатки конкретных видов. Затем тестовая сверка в "Инвентаризации" с переключателем "Это сверка продаж": отрицательная дельта по виду пишется как `Вид действия = "Продажа"` и не меняет агрегат; положительная дельта пишется как обычно и дополнительно зеркалится в агрегат; при выключенном переключателе отрицательная дельта тоже зеркалится в агрегат (как потеря).
- Баг с `onEditProduction`: ручной ввод "Производство" в "Реестр товаров" действительно списывает материалы по BOM и корректно блокирует при нехватке.
- Доступ: сторонний Google-аккаунт (не из списка) видит экран "Нет доступа".
